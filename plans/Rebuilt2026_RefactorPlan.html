Critical Performance Fixes — Loop Overruns
Risk: LOW — Rate-limiting and one-line deletions — No control logic changes — Do FIRST
Why this is Stage 0: The robot is showing WPILib loop overrun warnings: Loop time of 0.025s is greater than the expected 0.02s. Sustained overruns cause jerky driving, missed vision frames, and unreliable shooting. The four Critical-severity issues below are the primary causes. Fixing C-1 alone (one line) should eliminate the majority of overruns.

0-1: Delete System.gc() (Issue C-1) — Most impactful single-line fix

Java's GC runs when it needs to. Forcing it every 100ms causes more frequent stop-the-world pauses, not fewer. Even a minor GC can take 5–15ms; a major GC can exceed 50ms.

// DELETE from robotPeriodic() in Robot.java:
if (m_gcTimer.advanceIfElapsed(0.1)) {
    System.gc();
}
// Also delete the m_gcTimer field declaration

0-2: Rate-limit RobotStateMachine.periodic() telemetry (Issues C-2, C-3)

10+ SmartDashboard writes plus three NT struct publishes fire every 20ms. Each write serializes an object and dispatches a UDP packet. Wrap all display-only puts at 10 Hz. Also move updateTargetPose() to 10 Hz — the predicted target moves slowly enough for the turret PID to track.

private final Timer m_telemetryTimer = new Timer();

// In periodic():
if (m_telemetryTimer.advanceIfElapsed(0.1)) {
    SmartDashboard.putString("Robot/State", getState().toString());
    // ... all display-only puts
    posePublisher.set(currentPose);
    turretPosePublisher.set(turretPose);
    updateTargetPose();   // 10 Hz is sufficient
}
// targetPosePublisher stays every loop — drives AlignTurretToHub

0-5: Add bounds clamp to Turret.setPosition() (Issue M-2)

A bad angle from AlignTurretToHub could currently drive the turret into its hard stop.

public void setPosition(double degrees) {

If the PathPlanner GUI settings file is missing (common on a freshly-imaged RoboRIO), config is null and any auto command throws NullPointerException mid-match.

Shoot-on-the-Move Accuracy Fixes
Risk: MEDIUM — Changes active aiming math — Requires hardware testing
Current TOF table values (0.85–1.14 s for 1.8–5.2 m) are labeled // ! Fake values. A ball at 15 m/s exit speed travels 1.8 m in ~0.12 s — not 0.85 s. Wrong TOF values make lead compensation worse than no compensation.

3A: Measure and replace fake TOF values

Film shots at 240 fps minimum. Measure at each distance in the current table. Average 3 shots. Expected realistic values: ~0.10–0.30 s across 1.8–5.2 m. Update m_TOFMap in RangeFinder.java and remove the // ! Fake values comment.

3B: Wire turret-angle flywheel speed correction

The formula already exists in RangeFinder.getRotAdder(deg) but is not wired to the setpoint.

double correctedVelocity = RangeFinder.getShotVelocity(distance)
    + RangeFinder.getRotAdder(stateMachine.getConvertedTurretPosition());
m_Flywheel.setSpeed(correctedVelocity);

Validate the +2.83 RPS constant term at zero turret offset.

3C: Fix Bug 2 — radial speed correction unit issue

The TOF-iterated loop already computes the corrected distance — getShotVelocity(correctedDistance) inherently accounts for a longer/shorter shot. Remove any additional term that adds robot velocity (m/s) directly to flywheel RPS. Confirm UpToSpeedHopperShoot uses getTargetPose() distance, not raw HubPose.
